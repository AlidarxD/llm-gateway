# PII redaction middleware

`PIIMiddleware` (`gateway/middleware/pii/`) sits first in the pipeline (`pii -> cache -> provider`).

- **before**: finds PII in every message (`content` string or text parts, tool-call arguments),
  replaces it with stable placeholders (`<IIN_1>`, `<PHONE_2>`; the same value gets the same
  placeholder within a request). The mapping lives in `ctx.extra["_pii_vault"]` only. `PIIVault`
  has a value-free `repr` and refuses pickling, so an accidental `log(ctx)` cannot leak values.
- **after**: restores the originals in the response (content and tool-call arguments).
- **streaming**: the core aggregates for `before/after` (see CONTRACT.md). For forwarding SSE deltas
  directly use `PIIMiddleware.stream_restorer(ctx)`: `feed(delta)` holds back only a trailing
  fragment that may still become a placeholder (`<PHO` + `NE_1>`), `flush()` at the end.

## Modes (per API key)

```python
PIIMiddleware(
    PIIConfig(
        default_mode=PIIMode.REDACT, per_key={"key_ci": PIIMode.LOG_ONLY, "key_bank": PIIMode.BLOCK}
    )
)
```

| Mode | Behaviour |
|---|---|
| `redact` | placeholders sent to the provider, originals restored in the answer |
| `block` | short-circuits with a `ChatResponse` (`finish_reason="content_filter"`, `ctx.extra["pii_blocked"]=True`) |
| `log_only` | request untouched; entity **counts** go to `ctx.extra["pii_detected"]` and the `gateway.pii` logger (never values) |

## Detectors (code only, no LLM)

| Entity | Rule |
|---|---|
| `IIN` | 12 digits, valid birth date + century digit (1-6), KZ checksum (two weight passes mod 11) |
| `BIN` | 12 digits, month 01-12, type digit 4-6, subtype 0-3, same checksum |
| `CARD` | 13-19 digits (spaces/dashes allowed), Luhn, leading digit 2-6 |
| `IBAN` | `KZ` + 18 alnum (grouped or not), ISO 13616 mod-97 |
| `PHONE` | KZ/RU `+7`, `8`, `7` prefixes, any of the common separators/brackets; area code starting 3-9 |
| `EMAIL` | local@domain.tld |
| `PASSPORT` | `N` + 8 digits (KZ passport); 9-digit KZ ID card and RU 4+6 passport **only next to a keyword** (паспорт, удостоверение личности, жеке куәлік, passport, ID ...) |

Overlaps are resolved by detector priority (IBAN > CARD > IIN > BIN > EMAIL > PHONE > PASSPORT).
Add your own by implementing the `Detector` protocol (`entity`, `priority`, `find(text)`) and passing
`detectors=[*default_detectors(), MyDetector()]`.

## Quality

Dataset: 348 synthetic RU/KZ/EN texts generated by `tests/pii/pii_dataset.py` (seeded; no real
people's data): 7 entity types in 2-3 templates per language, multi-entity texts, plain negatives and
look-alike negatives (checksum-broken IIN/card/IBAN, order numbers, bare 9-digit numbers, short phones).
Exact span + type match. Reproduce: `uv run python benchmarks/pii_eval.py --markdown`.

| Entity | Precision | Recall | Support |
|---|---|---|---|
| IIN | 1.000 | 1.000 | 64 |
| BIN | 1.000 | 1.000 | 24 |
| PHONE | 1.000 | 1.000 | 64 |
| CARD | 1.000 | 1.000 | 44 |
| IBAN | 1.000 | 1.000 | 44 |
| EMAIL | 1.000 | 1.000 | 84 |
| PASSPORT | 1.000 | 1.000 | 24 |

**Read this honestly:** the dataset is written by the same author as the detectors, so 1.000 is a
sanity check, not a field estimate. Known gaps: names/addresses (not detected), IIN/BIN written with
spaces, ID numbers without a nearby keyword, phones with exotic separators. Checksums are covered by
`hypothesis` property tests (`tests/pii/test_pii_checksums.py`): generated valid values pass, any
single-digit change is rejected for Luhn, and wrong check digits are rejected for IIN/IBAN.
